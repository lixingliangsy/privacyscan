Privacy policy gaps AI products usually find first

A privacy-policy gap is any place where your published notice does not match what the product actually does with personal data. AI features create gaps quickly, because they add collection points that a template written before the feature existed never mentions.

Prompt and upload handling

When a user types a prompt or uploads a file, the text or binary often leaves the browser and goes to a model provider. I have seen many teams treat this as a transient step that does not need disclosure, but the moment the data can be linked to an individual it becomes personal data under GDPR and similar laws.

What leaves the device

  • The raw prompt string exactly as typed.
  • Any metadata attached to the upload (filename, timestamps, device ID).
  • Derived embeddings or vectors that the provider stores for caching.

Why notices miss it

Older privacy notices were written around account data and cookies. They list categories like “name”, “email”, “usage logs”. Prompt text and file uploads are not mentioned, so the notice is silent.

How to verify

  1. Run a test request with a unique identifier (e.g., a random UUID) in the prompt.
  2. Check the provider’s logs or your own ingestion pipeline to see if that identifier appears.
  3. If it does, treat the prompt as personal data and add a disclosure.

Inference logging and retention

Many products keep logs of prompts, outputs, and internal scores for debugging, abuse detection, or model monitoring. These logs are often retained longer than user‑account data, creating a mismatch.

What gets logged

  • The full prompt and the model’s raw output.
  • Timestamp, IP address, and session identifier.
  • Internal scores such as toxicity or confidence.

Linkability risk

If the log contains a user‑specific identifier (even a hashed email) or can be combined with other data to re‑identify a person, the log falls under personal data. I have seen cases where a simple session ID combined with a known IP range allowed re‑identification.

Disclosure checklist

  1. State that prompts and outputs are logged for abuse monitoring.
  2. Give the retention period (e.g., 90 days) and the criteria for earlier deletion.
  3. Explain whether logs are shared with any third party (including the model provider).
  4. Provide a way for users to request log deletion.

When you add these items, the notice moves from silent to explicit, closing a common gap.

New media categories (image, audio, file)

Early privacy templates rarely listed “image”, “audio”, or “generic file” as data types. AI features that accept these inputs create new collection points that the notice does not cover.

Why templates miss them

Templates were built around text fields and cookies. When a product adds an image‑upload‑to‑recognize‑objects feature, the notice still talks only about “user‑provided text”. The omission is a gap.

Re‑identification concerns

  • Images can contain faces, license plates, or location metadata.
  • Audio may capture voiceprints or background conversations.
  • Files may embed embedded personal data (e.g., a PDF with a scanned ID).

Even if the model does not store the raw file, the act of transmitting it to a third party is a transfer of personal data.

What to disclose

  1. List each media type you accept as a separate data category.
  2. Describe the purpose (e.g., “we extract objects from images to tag content”).
  3. Give the retention period for the raw file and any derived features.
  4. Note whether the file is sent to a model provider and where that provider is located.

Adding these lines makes the notice match the product’s actual behavior.

Automated decision‑making and profiling

When model output influences a user’s rights — such as granting a loan, showing a job, or moderating content — the notice must explain the logic and the consequences.

When output matters

  • A credit‑scoring model that decides interest rates.
  • A content‑ranking system that hides or shows posts.
  • A hiring tool that recommends candidates.

What the notice needs

  1. A clear statement that the decision is automated.
  2. A description of the input features used (e.g., “we use age, income, and past‑payment behavior”).
  3. An explanation of how the model turns those inputs into a score or category.
  4. Information about the right to obtain human review or to contest the outcome.

Many teams put a vague line like “we use AI to improve experience”. That is insufficient when the output has legal or material effects.

What this is NOT

I want to be honest about the limits of the advice above. This guide does not promise that following it will give you 100 % compliance, nor does it claim that you will never miss a gap.

Limitations of the checklist

  • The list covers common gaps seen in early‑stage AI products; it is not exhaustive.
  • Legal interpretation varies by jurisdiction; you should still consult counsel.
  • Technical changes (new model versions, new data flows) can introduce gaps after the notice is updated.

What we do not guarantee

  • We do not guarantee that a privacy scan will catch every possible misuse.
  • We do not guarantee that the notice will be understood by all users.
  • We do not guarantee that retention periods you state will be technically feasible in every system.

Treat this as a practical starting point, not a final certification.

Operator checklist for Privacy policy gaps AI products usually find first

I keep a written checklist next to every release that touches this topic. The list is boring on purpose: name the owner, name the evidence artifact, and name the rollback. If a step cannot produce a file, a ticket, or a log line, it is not a step — it is a wish.

Before you change production

  • Freeze the branch or config revision you will measure against.
  • Record the current failure mode with one concrete input and one concrete output.
  • Confirm which identity the job runs as, and whether that identity can reach data it should not.
  • Open the primary references you will cite: https://commission.europa.eu/strategy-and-policy/priorities-2019-2024/europe-fit-digital-age_en, https://genai.owasp.org/llmrisk/llm01-prompt-injection.

While you run the check

  • Prefer one reproducible path over ten anecdotal screenshots.
  • Write the expected safe outcome before you trigger the tool or query.
  • Capture the exact command, prompt, schema, or regex under test — not a paraphrase.
  • If the system can act (send, write, delete, transfer), require a confirmation boundary in the same pass.

After you finish

  • File residual risk with an owner and a date, even when the scan is clean.
  • Do not convert a green check into sales language that claims completeness.
  • Re-run the same checklist when the model, tool schema, or validation rules change.

Frequently asked questions

Is a prompt personal data?

It can be. If the prompt can be linked to an identified or identifiable person, it falls in scope and needs to be covered by the notice.

Do we need to name our model provider?

Recipients of personal data are normally disclosed. Naming the provider, or at least the category and location, is the safer disclosure.

Do we have to describe training use?

If user content is used to train or improve a model, say so plainly. Silence on that point is one of the most-read lines of any AI privacy notice.

How often should the policy be revisited?

On every material change to what you collect or which providers you use — for AI products, that is usually more often than once a year.
